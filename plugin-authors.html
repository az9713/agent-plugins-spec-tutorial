    Tutorial 1 — Build an Agent Plugin

    You package one skill and one MCP server into a directory that any conformant client can load. This page explains every key that you may write, and every rule that decides whether the client accepts it.

    Specification 1.0.0 Example: example/changelog-tools/ Build time: about 20 minutes
    About the comments in the JSON below

    JSON forbids a comment. The listings on this page add // comments to explain each key, and they are marked jsonc. The real files in example/ contain no comment. A comment in a real file makes the document invalid JSON, and the client rejects the plugin §5.2.

    1 · The package model

    Five rules define the package §4.1. Learn these first, because every later rule depends on them.

    1. A plugin is a directory at one filesystem location.
    2. The directory must contain plugin.json at its root.
    3. Every file that the client reads from the package must resolve inside the plugin root, after the operating system follows every symlink, junction, and reparse point.
    4. A configuration field that the specification defines as a plugin-relative path must begin with ./, and must still be inside the root after resolution.
    5. A value that the specification does not define as a path — a command argument, an environment value — is an opaque string. The client does not treat it as a package path.

    1.1 Which paths are legal

    ValueLegalWhy
    ./bin/serverYesIt starts with ./, and it stays inside the root.
    ./dataYesSame reason.
    ./sub/../bin/serverYesIt starts with ./, and it still resolves inside the root.
    bin/serverNoA plugin-relative path must begin with ./.
    ../bin/serverNoIt escapes the plugin root.
    /usr/bin/serverNoAn absolute path is not a plugin-relative path.
    A symlink whose target is inside the rootYesExplicitly allowed §4.1.
    A symlink whose target is outside the rootNoThe client must reject the resolved path.
    What containment does not do

    These rules govern the files that the package supplies. They do not sandbox your subprocess, and they do not restrict a path that the user types at run time §4.1. A stdio server that you launch can still read the whole filesystem. Version 1 has no sandbox.

    1.2 The standard layout

    text
    my-plugin/
├── plugin.json              # REQUIRED. The manifest.                    §5
├── skills/                  # OPTIONAL. Fixed location for skills.       §6.1
│   └── summarize/
│       ├── SKILL.md
│       ├── scripts/
│       └── references/
├── mcp.json                 # OPTIONAL. Fixed location for MCP servers.  §6.1
├── com.example.client/      # OPTIONAL. A client extension directory.    §8.2
│   └── hooks/
├── LICENSE
└── CHANGELOG.md

    The two component locations are fixed. plugin.json cannot move them, and it cannot hold inline component configuration §6.1.

    2 · The manifest, key by key

    The manifest schema is closed. Exactly ten top-level keys are permitted, and no other key §5.2. Here is the complete manifest of the example, with every key explained.

    jsoncchangelog-tools/plugin.json
    {
  // REQUIRED (§5.3). The canonical schema identifier.
  // The value tells the client WHICH specification version to apply.
  // For version 1.0.0 the value MUST be exactly this string.
  // The client MUST NOT download this URL while it loads the plugin (§5.2).
  // An unrecognized value makes the client REJECT the whole plugin.
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",

  // REQUIRED (§5.3). The plugin name. Four constraints apply (§5.5):
  //   length        1 to 64 characters inclusive
  //   character set a-z, 0-9, hyphen, period — lowercase only
  //   first / last  must be alphanumeric
  //   repetition    no "--" and no ".."
  // A violation REJECTS the whole plugin.
  "name": "changelog-tools",

  // OPTIONAL (§5.4). The package version.
  // Semantic Versioning is RECOMMENDED, not required.
  // The client MUST NOT reject the plugin because this is not SemVer (§5.4).
  // A client MAY use the value to detect an update and to expire a cache (§10.2).
  "version": "1.2.0",

  // OPTIONAL (§5.4). One short sentence about the purpose of the plugin.
  "description": "Writes changelog entries and stores release notes.",

  // OPTIONAL (§5.4). An object with THREE permitted keys and no other key.
  // Any extra key, or a non-string value, REJECTS the whole plugin.
  "author": {
    "name": "Simon",              // OPTIONAL string.
    "email": "az9713@yahoo.com",  // OPTIONAL string. The format is NOT verified.
    "url": "https://example.com"  // OPTIONAL string. The format is NOT verified.
  },

  // OPTIONAL (§5.4). The documentation URL. The format is NOT verified.
  "homepage": "https://example.com/changelog-tools",

  // OPTIONAL (§5.4). The source repository URL. The format is NOT verified.
  "repository": "https://github.com/example/changelog-tools",

  // OPTIONAL (§5.4). The license. An SPDX identifier is RECOMMENDED, not required.
  "license": "MIT",

  // OPTIONAL (§5.4). An array of strings, for search and for discovery.
  // A non-string element REJECTS the whole plugin.
  "keywords": ["changelog", "release", "notes"],

  // OPTIONAL (§5.6, §8.1). Client-specific data.
  // Each KEY is a reverse-domain namespace that one client owns.
  // Each VALUE must be an object. Agent Plugins gives the contents no meaning.
  // A client that does not own the namespace ignores the value, and does not
  // validate it. Your plugin therefore stays portable.
  "extensions": {
    "com.example.client": {
      "autoEnable": true
    }
  }
}

    2.1 The ten keys as cards

    $schema

    Requiredstring§5.2, §5.3

    The canonical identifier https://agent-plugins.org/schemas/1.0.0/plugin.schema.json. Nothing else is valid for version 1.0.0.

    The client uses the value to select local validation rules. It never fetches the URL during a load. When the client supports no matching version, it rejects the plugin and should report the unsupported version.

    name

    Requiredstring§5.3, §5.5

    The plugin name. See section 2.3 for every constraint and for worked examples.

    version

    Optionalstring§5.4, §10.2

    Any string. SemVer is recommended: major for a breaking change, minor for a backward-compatible feature, patch for a backward-compatible fix.

    A client may use the value for update detection and for cache freshness. A client must not reject the plugin because the string is not SemVer.

    description

    Optionalstring§5.4

    A short description of the purpose. No length constraint exists in the specification.

    author

    Optionalobject§5.4

    A closed object. It accepts name, email, and url, each a string. Any other key, or a non-string value, is fatal: the client rejects the plugin.

    The client does not verify that email looks like an email address, or that url looks like a URL.

    homepage

    Optionalstring§5.4

    A documentation or home page URL. The format is not verified.

    repository

    Optionalstring§5.4

    A source repository URL. The format is not verified.

    license

    Optionalstring§5.4

    A license identifier. An SPDX identifier is recommended. A non-SPDX string is not a rejection reason.

    keywords

    Optionalstring[]§5.4

    Search and discovery tags. Every element must be a string. A non-string element rejects the plugin.

    extensions

    Optionalobject§5.6, §8.1

    An object whose keys are reverse-domain namespaces and whose values are objects.

    Two different failure rules apply here, and the difference matters:

    • "extensions": "text" — the field is not an object. Non-fatal. The client reports it, ignores it, and continues §8.1.
    • "extensions": { "com.x": "text" } — a member value is not an object. Fatal. The client rejects the plugin §8.1.

    2.2 What each error does

    Exactly two manifest problems are non-fatal. Every other problem rejects the whole plugin: no skill is discovered, and no server starts §5.2, §11.3.

    ProblemResultSection
    An unknown top-level key, for example "tools": []Non-fatal — reported, ignored, loading continues§5.2
    extensions is not an objectNon-fatal — reported, ignored, loading continues§8.1
    plugin.json is missingFatal — the plugin is rejected§5.1
    plugin.json is not valid JSON, or is not an objectFatal§5.2
    $schema is missing, or is unrecognizedFatal§5.2, §5.3
    name is missing, empty, or breaks a constraintFatal§5.3, §5.5
    Any permitted key has the wrong JSON typeFatal§5.2
    author holds a fourth keyFatal§5.4
    An extensions member value is not an objectFatal§8.1
    Trap

    An unknown top-level key is still a schema violation. The client reports it. Do not treat the non-fatal rule as permission to invent a key. Put client-specific data under extensions §5.2.

    2.3 The name constraints in detail

    ConstraintRequirement
    Length1 to 64 characters inclusive.
    Character seta-z, 0-9, -, and . only. Lowercase only.
    First and last characterAlphanumeric.
    RepetitionNo --. No ...
    NameValidReason
    my-pluginYesEvery rule holds.
    acme.toolsYesA period is allowed inside the name.
    lint3rYesDigits are allowed.
    aYesOne character satisfies the length rule.
    My-PluginNoUppercase.
    -startNoThe first character is not alphanumeric.
    end-NoThe last character is not alphanumeric.

    One regular expression enforces all four constraints, apart from the maximum length:

    regex
    /^(?!.*(?:--|\.\.))[a-z0-9](?:[a-z0-9.-]*[a-z0-9])?$/

    3 · Skills

    3.1 Where the client looks

    The location is fixed at skills/ §6.1. The client reads each immediate child directory. A child that contains a regular file named exactly SKILL.md is one skill. The client does not search deeper §7.1.

    text
    skills/
├── changelog-entry/
│   └── SKILL.md            ✓ discovered. The skill name is "changelog-entry".
├── notes/
│   └── README.md           ✗ ignored. There is no SKILL.md file.
├── deep/
│   └── nested/
│       └── SKILL.md        ✗ ignored. The client does not recurse.
└── SKILL.md                ✗ ignored. A skill needs its own directory.
    ConditionClient behaviorSection
    skills/ does not existNot an error. The client loads the other component types.§6.2
    skills exists but is a fileThe skill component type is invalid. Other types still load.§6.2
    A child directory has no SKILL.mdIgnored silently.§7.1
    A SKILL.md resolves outside the rootThat skill is skipped. Other skills still load.§4.1, §7.1
    A SKILL.md breaks the Agent Skills specificationThat skill is skipped and reported. Other skills still load.§7.1

    3.2 What goes inside a skill

    Agent Plugins does not define the SKILL.md format. The Agent Skills specification defines the frontmatter, the body, and the support directories scripts/, references/, and assets/ §7.1. Agent Plugins defines the discovery only.

    markdownskills/changelog-entry/SKILL.md
    ---
name: changelog-entry
description: Write a Keep a Changelog entry from a list of merged pull requests.
  Use when the user asks for a changelog, a release note, or a version summary.
---

# Changelog entry

Write one changelog entry for one version.

## Procedure

1. Read `references/format.md` for the required section order.
2. Group each change into one section: Added, Changed, Deprecated,
   Removed, Fixed, Security.
3. Write one line for each change. Start each line with a verb.
4. Add the version and the date: `## [1.2.0] - 2026-08-06`.
5. Run `scripts/check_entry.py <file>` to verify the section order.
    Rule

    The description field decides whether the model loads the skill at all. Name the trigger, not only the topic. "Use when the user asks for a changelog" beats "About changelogs".

    4 · MCP servers

    4.1 The file

    The location is fixed at mcp.json in the plugin root. You cannot put MCP configuration inside plugin.json, and you cannot use another path §7.2.1.

    The file has exactly two top-level keys, and no other key. An empty mcpServers object is valid §7.2.1.

    KeyRequiredTypeMeaning
    $schemaYesstringThe canonical MCP schema identifier. Its version must match plugin.json §10.1.
    mcpServersYesobjectEach key names a server. Each value is a closed server object.

    4.2 The stdio transport, key by key

    A stdio server runs as a subprocess on the user's machine.

    jsoncchangelog-tools/mcp.json — the stdio entry
    {
  // REQUIRED. The canonical MCP schema identifier for the SAME version as plugin.json.
  // A version mismatch disables MCP for this plugin. The skills still load (§7.2.2).
  "$schema": "https://agent-plugins.org/schemas/1.0.0/mcp.schema.json",

  // REQUIRED. An object. Each key is a server name. An empty object is valid (§7.2.1).
  "mcpServers": {

    "notes": {
      // REQUIRED. "stdio" selects a local subprocess.
      // The variant is CLOSED: a key from another variant (url, headers) makes
      // THIS ENTRY invalid. The other entries still load (§7.2.2).
      "type": "stdio",

      // REQUIRED. ONE executable token. NOT a shell command string (§7.2.1).
      //   "python"           ✓ a bare name — the platform executable search resolves it
      //   "./bin/server"     ✓ a plugin-relative path — resolved against the plugin root
      //   "python -u x.py"   ✗ two tokens — put the rest in "args"
      //   "../bin/server"    ✗ escapes the plugin root (§4.1)
      // NO placeholder expands in this field (§9.2).
      // A bundled executable MUST use "./". A conformant plugin MUST NOT depend on
      // the configured PATH, because PATH behavior is client-defined (§7.2.1).
      "command": "python",

      // OPTIONAL. An array of strings passed to the executable.
      // ${PLUGIN_ROOT} and ${PLUGIN_DATA} DO expand here (§9.2).
      "args": ["${PLUGIN_ROOT}/bin/notes_server.py"],

      // OPTIONAL. An object of string values.
      // The VALUES expand. The KEYS do not (§9.2).
      // The keys PLUGIN_ROOT and PLUGIN_DATA are FORBIDDEN — the client supplies both,
      // and such a key makes THIS ENTRY invalid (§9.2).
      // These values are visible package data. NEVER store a secret here.
      "env": {
        "NOTES_FILE": "${PLUGIN_DATA}/notes.jsonl",
        "PYTHONUNBUFFERED": "1"
      },

      // OPTIONAL. The working directory of the subprocess.
      // Omitted  -> the client uses the PLUGIN ROOT (§7.2.1).
      // Only three forms are legal:
      //   "./data"          a plugin-relative path
      //   "${PLUGIN_ROOT}"  or "${PLUGIN_ROOT}/sub"
      //   "${PLUGIN_DATA}"  or "${PLUGIN_DATA}/sub"
      // Any other form — "data", "/tmp", "~/x" — makes THIS ENTRY invalid.
      // The client expands first, then checks containment against the matching base.
      "cwd": "${PLUGIN_ROOT}"
    }
  }
}
    KeyRequiredTypeExpandsNotes
    typeYes"stdio"NoSelects the transport.
    commandYesstringNoOne token. Bare name, or a ./ path.
    argsNostring[]YesPassed to the executable.
    envNoobject of stringsValues onlyReserved names are forbidden.
    cwdNostringYesThree legal forms. Default: the plugin root.
    The most common stdio mistake

    "command": "npx -y @scope/server" is invalid. The field holds one token. Write "command": "npx" and "args": ["-y", "@scope/server"]. The specification treats the field as one token so that no client has to parse or escape a user-authored shell string §7.2.1.

    4.3 The remote transports, key by key

    jsoncchangelog-tools/mcp.json — the remote entries
    {
  "$schema": "https://agent-plugins.org/schemas/1.0.0/mcp.schema.json",
  "mcpServers": {

    "release-api": {
      // REQUIRED. "streamable-http" selects the CURRENT MCP Streamable HTTP transport.
      "type": "streamable-http",

      // REQUIRED. An absolute http or https URL.
      //   MUST NOT contain user information — "https://user:pw@host/mcp" is invalid.
      //   MUST NOT contain a fragment      — "https://host/mcp#x"        is invalid.
      //   https is MANDATORY, except when the host is exactly "localhost"
      //   or an IP literal in a loopback range (§7.2.1).
      // NO placeholder expands here (§7.2.1).
      "url": "https://releases.example.com/mcp",

      // OPTIONAL. Fixed HTTP headers for the configured origin.
      //   Header names are case-insensitive. The same name twice under a different
      //   casing makes THIS ENTRY invalid.
      //   NO placeholder expands in a name or in a value.
      //   A client header for HTTP, MCP, or authorization OVERRIDES a header here.
      //   The client MUST NOT forward these headers to another origin after a
      //   redirect without explicit user authorization.
      // Visible package data. NEVER store a credential here (§7.2.1).
      "headers": {
        "X-Tenant": "public-tenant"
      }
    },

    "legacy-feed": {
      // "sse" selects the DEPRECATED HTTP+SSE transport of MCP 2024-11-05.
      // It does NOT mean an SSE stream inside Streamable HTTP.
      // Client support for "sse" is OPTIONAL. Many clients skip this entry (§7.2.1).
      "type": "sse",
      "url": "https://legacy.example.com/sse"
    }
  }
}
    URLValidReason
    https://api.example.com/mcpYesAbsolute, HTTPS, no user info, no fragment.
    http://localhost:8080/mcpYesPlain HTTP is allowed for localhost.
    http://127.0.0.1/mcpYesA loopback IP literal.
    http://api.example.com/mcpNoPlain HTTP to a non-loopback host.
    https://u:p@api.example.com/mcpNoUser information in the authority.
    https://api.example.com/mcp#topNoA fragment.
    /mcpNoNot absolute.
    wss://api.example.com/mcpNoThe scheme must be http or https.

    4.4 Which transport a client must support

    A client that supports MCP must support stdio or streamable-http, and should support both. Support for sse is OPTIONAL. The client uses the declared transport for the first connection, and the specification defines no fallback §7.2.1.

    Consequence for you

    A plugin that offers only an sse server may load no server at all on a conformant client. Offer streamable-http as well, under a second server name.

    4.5 What each MCP error does

    ProblemBlast radiusSection
    mcp.json is missingNothing. Absence is not an error.§6.2
    mcp.json is a directoryMCP is disabled for the plugin. Skills still load.§6.2
    Invalid JSON, a wrong top-level key, or a version mismatchMCP is disabled for the plugin. Skills still load.§7.2.2
    One server entry is invalidThat entry only. Other servers still load.§7.2.2
    The client does not support the transportThat entry only.§7.2.2
    The server fails to start, connect, or authenticateThat connection only. Everything else still loads.§7.2.2
    Authorization

    Version 1 defines no OAuth configuration and no portable credential reference. Discovery, the user interaction, and the credential storage belong to the client. An authorization failure counts as a connection failure, not as invalid configuration §7.2.1.

    5 · The two plugin variables

    The client sets exactly two environment variables for every plugin subprocess §9.1.

    VariableValueLifetimeUse it for
    PLUGIN_ROOTThe absolute path of the plugin directory.Replaced on every update.Bundled scripts, binaries, and configuration that ship with the package.
    PLUGIN_DATAThe absolute path of a writable directory that the client manages for this installed plugin.Survives an update. May be deleted on uninstall.Installed dependencies, a virtual environment, generated code, a cache, and any state.
    The rule that costs data

    An update replaces the contents of PLUGIN_ROOT. Anything that your server writes there disappears. Write every persistent file under ${PLUGIN_DATA} §9.1.

    5.1 The expansion rules

    FieldExpands
    Each element of argsYes
    Each value in envYes
    cwdYes
    A key in envNo
    commandNo
    url, a header name, a header valueNo
    A fixed component locationNo

    Five rules govern the replacement §9.2:

    1. Only ${PLUGIN_ROOT} and ${PLUGIN_DATA} expand. Nothing else expands.
    2. Expansion works only in the three fields marked above.
    3. Expansion is one pass. The client never scans the inserted text again.
    4. Unknown placeholder text stays literal. ${HOME} remains the six characters ${HOME}.
    5. An env object that declares PLUGIN_ROOT or PLUGIN_DATA makes that server entry invalid.

    5.2 The order of the environment

    The client builds the subprocess environment in this order §9.1:

    1. The client chooses a base environment. It may inherit, omit, or clean the ambient variables.
    2. The client expands your env values, and lays them over the base. A same-name entry replaces the base entry, under the platform name semantics. Windows names are case-insensitive.
    3. The client sets PLUGIN_ROOT and PLUGIN_DATA last. Your value can never win.
    Rule

    Apart from the platform executable search that resolves a bare command, a conformant plugin must not depend on any inherited variable that the specification does not require §9.1. If your server needs HOME or PATH, supply the value explicitly in env, or read it defensively.

    5.3 How the example server uses both variables

    pythonbin/notes_server.py — the relevant lines
    # The client sets PLUGIN_ROOT and PLUGIN_DATA. mcp.json expands ${PLUGIN_DATA}
# into NOTES_FILE. This server never writes inside PLUGIN_ROOT, because a plugin
# update replaces the package contents.
NOTES_FILE = os.environ.get("NOTES_FILE") or os.path.join(
    os.environ.get("PLUGIN_DATA", "."), "notes.jsonl"
)

    The fallback matters. The server reads NOTES_FILE first, because mcp.json supplies it. It falls back to PLUGIN_DATA, because the client always sets that variable.

    6 · Client extensions

    You need a client-specific feature that version 1 does not define — a hook, a slash command, a custom agent. Use a reverse-domain namespace that the client owns §8.

    Two representations exist. You may use either, or both:

    RepresentationWhereExample
    Manifest dataA key inside extensions in plugin.json"com.example.client": { "autoEnable": true }
    FilesA top-level directory with exactly that namecom.example.client/hooks/hooks.json
    text
    changelog-tools/
├── plugin.json                 # holds extensions: { "com.example.client": { ... } }
└── com.example.client/         # holds the FILES for the same namespace
    └── hooks/
        └── hooks.json
    Why this keeps you portable

    Agent Plugins assigns no discovery, validation, loading, or failure meaning to extension data §8. A client that does not implement com.example.client ignores the namespace without validating it §8.1, and still loads your skills and your MCP servers. One package therefore works everywhere, and gains extra behavior only on the client that understands it.

    8 · Build the example, step by step

    1. Create the directory changelog-tools/.
    2. Write plugin.json with $schema and name. Add the metadata from section 2.
    3. Create skills/changelog-entry/, and write SKILL.md inside it.
    4. Add references/format.md and scripts/check_entry.py in the same skill directory.
    5. Write bin/notes_server.py. Read the target path from the NOTES_FILE variable.
    6. Write mcp.json. Point args at ${PLUGIN_ROOT}/bin/notes_server.py.
    7. Point NOTES_FILE at ${PLUGIN_DATA}/notes.jsonl, never at ${PLUGIN_ROOT}.
    8. Run cd example/client && npm test to confirm the client works.
    9. Run npm run load-example. Confirm the output lists the skill and two servers.

    10 · Author checklist

    • plugin.json exists in the plugin root.
    • $schema equals https://agent-plugins.org/schemas/1.0.0/plugin.schema.json.
    • name passes all four constraints of §5.5.
    • No extra top-level key, and no extra author key.
    • Each skill sits at skills/<name>/SKILL.md, exactly one level deep.
    • Each SKILL.md conforms to the Agent Skills specification.
    • mcp.json, when present, declares the same specification version as plugin.json.
    • Each command value is one token.
    • Every package path starts with ./ and stays inside the root.
    • No secret appears in env or in headers.
    • Every writable path uses ${PLUGIN_DATA}.
    • Client-specific data sits under a reverse-domain namespace.
    • At least one MCP server uses stdio or streamable-http, not only sse.
