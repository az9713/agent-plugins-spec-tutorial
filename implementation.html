    The implementations

    This page describes the code that ships in example/: the worked plugin, the two reference clients, and the bundled MCP server. It then answers one question with measurements instead of assurances — is the code printed in the tutorial the code that actually runs? The short answer is yes for every block that claims to be a file, and 90 % for the TypeScript excerpts. The last section names every line of the difference and the reason for it.

    No dependency

    Every Python file imports the standard library only. The TypeScript client needs typescript and @types/node to compile, and nothing at run time. That is deliberate: a reader must be able to run the whole tutorial without trusting a package.

    The plugin

    The manifest carries no behavior

    plugin.json declares identity and nothing else. The client reads it, validates it, and then looks for components by directory convention, not by a list inside the manifest. There is no "skills": [...] array anywhere in the standard. That single design choice explains most of the client code: discovery is a filesystem walk, so containment and symlink resolution do the work that a declared list would otherwise do.

    The example uses all ten keys so that the tutorial can annotate each one. Only two are required: $schema and name. A plugin with those two keys and one skill directory is valid, and check 22 builds exactly that plugin and loads it.

    Three servers, one per transport

    jsonexample/changelog-tools/mcp.json — the shipping file, uncommented
    {
  "$schema": "https://agent-plugins.org/schemas/1.0.0/mcp.schema.json",
  "mcpServers": {
    "notes": {
      "type": "stdio",
      "command": "python",
      "args": ["${PLUGIN_ROOT}/bin/notes_server.py"],
      "env": {
        "NOTES_FILE": "${PLUGIN_DATA}/notes.jsonl",
        "PYTHONUNBUFFERED": "1"
      },
      "cwd": "${PLUGIN_ROOT}"
    },
    "release-api": {
      "type": "streamable-http",
      "url": "https://releases.example.com/mcp",
      "headers": { "X-Tenant": "public-tenant" }
    },
    "legacy-feed": {
      "type": "sse",
      "url": "https://legacy.example.com/sse"
    }
  }
}

    The three entries do three different jobs in the demonstration:

    1. notes is real and runs. The client builds a launch plan from it, and the demonstration starts that exact process and speaks MCP to it.
    2. release-api is valid but never contacted. Its host does not exist. It proves the client accepts and plans a remote transport; it does not prove any HTTP code works, because there is none.
    3. legacy-feed exists to be skipped. Support for sse is OPTIONAL §7.2.1. The client drops that one entry, prints server legacy-feed skipped: transport sse is unsupported, and still loads the other two servers and the skill. That one line is the whole failure-isolation rule, observable.

    The MCP server: 106 lines, line-delimited JSON-RPC

    bin/notes_server.py reads one JSON object per line from standard input and writes one per line to standard output. It answers initialize, tools/list and tools/call, returns null for a notification, and returns a JSON-RPC error for an unknown method or an unknown tool. It advertises protocol version 2025-06-18.

    Its one interesting line is where it decides to write:

    pythonbin/notes_server.py
    NOTES_FILE = os.environ.get("NOTES_FILE") or os.path.join(
    os.environ.get("PLUGIN_DATA", "."), "notes.jsonl"
)

    The server never resolves a path itself. The client sets PLUGIN_DATA, and mcp.json expands it into NOTES_FILE. The server writes where it is told. That is the correct division: a plugin update replaces the package contents, so anything written inside ${PLUGIN_ROOT} disappears on the next update §9.1. Check 16 takes a snapshot of every file in the plugin directory before and after the run and fails if a single byte changed.

    A known ceiling

    The read loop calls json.loads(line) without a guard. A malformed line raises and kills the server. That is acceptable in a 106-line teaching example — an MCP SDK handles framing and error recovery for you — but it is a real limit, it is untested, and the test page names it rather than hiding it.

    The skill is prose plus two files

    SKILL.md holds YAML frontmatter (name, description) and a short procedure. The procedure points at two sibling paths: references/format.md to read, and scripts/check_entry.py to run. Neither path is declared anywhere. The skill refers to them by relative path, and the client never needs to know they exist.

    check_entry.py enforces the section order Added → Changed → Deprecated → Removed → Fixed → Security, and the heading form ## [1.2.0] - 2026-08-06. It exits 0 on a valid entry and 1 with a reason on an invalid one.

    The extension directory has no meaning

    plugin.json declares extensions: { "com.example.client": { "autoEnable": true } } and the plugin ships a matching com.example.client/ directory. Agent Plugins gives the contents of neither one any meaning §8.1. A client that does not own the namespace must ignore the value and must not validate it. Both reference clients do exactly that: they carry the object through to the caller untouched and never look inside. That is what keeps a plugin portable across clients that each want their own extras.

    The two reference clients

    Same specification, same behavior, two languages. loader.py is 357 lines, loader.ts is 484 lines and compiles under strict. The difference in size is type declarations and narrowing, not extra logic.

    The six steps

    1. Resolve the root. realpath first, so every later containment test compares resolved paths and a symlink cannot smuggle a path out of the plugin §4.1.
    2. Read plugin.json. Missing, unparsable, wrong $schema, or an invalid name rejects the whole plugin.
    3. Validate the manifest. An unknown top-level key is dropped with a report, not a rejection §5.2. A wrong type on a known key rejects — except extensions, which is dropped with a report §8.1.
    4. Discover skills. Immediate children of skills/ that contain a SKILL.md §7.1. A nested SKILL.md is not a skill. A missing skills/ directory is not an error §6.2.
    5. Plan the MCP servers. Per-entry validation. One bad entry is skipped and reported; the rest still load §7.2.2.
    6. Return the extensions untouched.

    Three levels, and the code makes them structural rather than a matter of care:

    Expansion is one pass, and that is enforced

    Only ${PLUGIN_ROOT} and ${PLUGIN_DATA} expand, only in args, env values and cwd, and the replacement text is never scanned again §9.2. Both clients implement it as a single regular-expression substitution with a callback — never as chained .replace() calls, because chaining rescans and lets a value that contains a placeholder expand a second time. Both self-checks assert the non-recursive property directly:

    pythonloader.py — the self-check
    assert expand("${PLUGIN_ROOT}", "${PLUGIN_DATA}", "/d") == "${PLUGIN_DATA}"

    Read that carefully: the root is the literal text ${PLUGIN_DATA}. A one-pass implementation returns it unchanged. A rescanning implementation returns /d.

    Where PLUGIN_DATA points

    pythonloader.py
    default_data = os.path.join(os.path.dirname(root), ".plugin-data", os.path.basename(root))

    Outside the package, beside it. The client creates the directory before it launches anything, and sets PLUGIN_ROOT and PLUGIN_DATA last, after the plugin's own env, so a plugin cannot override either one. A plugin that tries to set them in env has that entry rejected instead §9.2.

    Where the two clients differ

    In behavior: nowhere that can be observed. Check 21 runs both against the example, normalizes path spelling (backslash to slash, drive-letter case), and compares the entire result structure — not a summary, the whole tree. The check has failed for a real reason during development, so it is not decorative.

    In construction, three differences worth knowing:

    • TypeScript declares an explicit Plugin result type and a Report callback type. Python uses plain dictionaries.
    • TypeScript narrows every unknown before use, which is most of the extra 127 lines.
    • Python's regular expressions and JavaScript's differ in syntax for the same rules. The name rule is the one place both spell it identically, and check 38 asserts the two source strings are equal character for character.

    Why the SKILL.md block is not the whole file

    Two differences, both deliberate:

    1. The page wraps the description across two lines to fit the column. YAML permits the continuation, so the meaning is unchanged. Check 42 unwraps the whitespace before comparing, and the name and description then match exactly.
    2. The page stops after the procedure and omits the file's final ## Rules section. The page is teaching the shape of a skill — frontmatter, then instructions — and the rules are about changelog style, not about the standard.

    The rule this page follows

    A block that says it is a file must be that file, and a machine re-checks it. A block that is an excerpt or an illustration may differ, and the difference must be nameable. Every difference above is named, counted, and reproducible with one command.

    What the tutorial never shows

    • loader.py is never quoted. The tutorial teaches the client in TypeScript. Python is the behavioral twin, and it earns its place through check 21 — identical output on the same input — rather than through quotation. Read the file; it is the shorter of the two.
    • The two JSON Schemas in reference.html are not shipped as files. No .schema.json exists in this repository, and the $schema URLs are identifiers the client compares as strings — a conformant client must not fetch them while it loads a plugin §5.2. Checks 55 to 59 therefore verify only that the printed schemas are consistent with the real manifests: every required key is present in the real file, and every key of the real file is declared in the schema. Nothing validates the manifests against the schemas with a real validator, because that would need a dependency.
    • This page and the test page are not scanned by the drift check. Part B reads the four tutorial pages only. See the reason.
