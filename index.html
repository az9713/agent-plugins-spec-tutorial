    What the standard actually is

    A plugin is one directory. The directory holds one manifest file and optional components. There is no archive format, no registry protocol, and no install command in the specification §4.1.

    ConceptDefinitionSection
    PluginA self-contained directory with a manifest and optional components.§3
    Plugin rootThe top-level directory of the package.§3
    ManifestThe file plugin.json in the plugin root. Mandatory.§5.1
    ComponentA skill or an MCP server entry. Version 1 defines these two, and no other.§7
    ClientA tool that discovers, installs, loads, and runs the components.§3
    Extension namespaceA reverse-domain identifier that one client owns, for example com.example.client.§8
    The one-sentence summary

    Agent Plugins defines where a client looks and what a client must accept or reject. It does not define how a client shows a skill, where a plugin comes from, or whether a user trusts it.

    The smallest valid plugin

    Three files. This plugin conforms.

    text
    hello-plugin/
├── plugin.json
└── skills/
    └── greet/
        └── SKILL.md
    jsonplugin.json
    {
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "hello-plugin"
}

    Two keys are required: $schema and name §5.3. Everything else is optional. A client that supports skills now finds the skill greet at skills/greet/SKILL.md §7.1.

    The example used throughout

    Both tutorials use one plugin. It helps a developer write release notes. It exercises every feature of the specification: all ten manifest keys, all three MCP transports, both plugin variables, a bundled executable, and a client extension.

    textexample/changelog-tools/
    changelog-tools/
├── plugin.json                       # the manifest — all 10 keys       (§5)
├── mcp.json                          # 3 servers, 3 transports          (§7.2)
├── skills/
│   └── changelog-entry/
│       ├── SKILL.md                  # the skill itself                 (§7.1)
│       ├── references/format.md      # support material
│       └── scripts/check_entry.py    # a helper script
├── bin/
│   └── notes_server.py               # a bundled, working MCP server
└── com.example.client/               # a client extension directory     (§8.2)
    └── hooks/hooks.json

    The plugin gives an agent two capabilities:

    1. A skill that teaches the changelog format, with a reference file and a validator script.
    2. An MCP server that stores release notes in a file, and keeps them between sessions.

    Run everything yourself

    Two reference clients ship with this tutorial. Both implement the same specification, and both produce the same result.

    shellTypeScript
    cd example/client
npm install
npm test              # runs the self-check: 30+ conformance cases
npm run load-example  # loads ../changelog-tools and prints the launch plan
    shellPython
    cd example/client
python loader.py                  # runs the same self-check
python loader.py ../changelog-tools

    Expected output from the load, shortened:

    jsonoutput
    {
  "name": "changelog-tools",
  "skills": [ { "name": "changelog-entry", "path": ".../skills/changelog-entry/SKILL.md" } ],
  "servers": {
    "notes":       { "type": "stdio", "command": "python", "...": "..." },
    "release-api": { "type": "streamable-http", "url": "https://releases.example.com/mcp" }
  },
  "reports": [ "server legacy-feed skipped: transport sse is unsupported" ]
}
    Read the report line

    The third server, legacy-feed, uses the deprecated sse transport. Support for sse is OPTIONAL §7.2.1. The client skips that one entry, reports the reason, and still loads the other two servers and the skill. That is the failure-isolation rule of the specification in action §7.2.2.

    What version 1 deliberately leaves out

    Do not design around these. They do not exist yet, and the project records them as future work.

    AbsentConsequence today
    A permission model, a capability declaration, and a sandboxThe client owns the trust prompt. A plugin cannot declare what it needs.
    Signature and provenance verificationA client cannot verify the origin of a package through the standard.
    A portable secret mechanismNever put a credential in env or in headers. Both are visible package data.
    Enterprise allowlist, blocklist, and central overridePolicy is a client feature.
    A standard audit event schemaReporting is required, but the format is yours.
    Dependencies between pluginsEach plugin must be self-contained.
    A standard validator and a conformance suiteTest with your own cases. This tutorial supplies a starting set.
    Commands, hooks, agents, rules, and LSP serversNot component types. Use a client extension namespace §8.
