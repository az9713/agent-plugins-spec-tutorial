    The 59 checks

    example/e2e.py is 537 lines that run the whole tutorial and report 59 results. This page lists every one: what it does, and what breaking would look like. It then does the part that most test documentation skips — it names what is not tested and why, and it states plainly what 59 green results do and do not entitle you to believe.

    59 checks Part A: 29 · Part B: 30 ~5 s Exit 0 = all passed

    Running it

    shellfrom the repository root
    python example/e2e.py           # prints the MCP transcript
python example/e2e.py --quiet   # prints the results only

    Python only. The TypeScript comparison prints [SKIP] instead of failing when Node is absent. The two parts do different jobs:

    • Part A — does it run? Load the plugin with the reference client, then launch the bundled MCP server from the client's own launch plan and speak the protocol to it.
    • Part B — does the tutorial describe what exists? Compare every code block on the four tutorial pages against the files in example/.

    Part A · A1 — the client loads the plugin

    Runs the command the front page tells the reader to run, python loader.py ../changelog-tools, and inspects the JSON it prints. Nothing is imported privately; the test uses the documented entry point.

    #CheckWhat it would catch
    1the Python loader loads the example pluginA crash, a non-zero exit, or unparsable output. The floor: the documented command works at all.
    2the loader finds the skill changelog-entryBroken discovery of skills/*/SKILL.md §7.1, or a skill silently dropped.
    3the loader keeps the stdio and streamable-http serversA valid entry wrongly rejected. Both supported transports must survive.
    4the loader skips the sse server and reports whyFailure isolation broken in either direction: an unsupported transport accepted, or one bad entry taking the whole file down §7.2.2. The report text is compared exactly.
    5the client extension namespace survives the loadA client mangling or dropping extensions, which would make the plugin non-portable §8.1.
    6NOTES_FILE expands into PLUGIN_DATA, not PLUGIN_ROOTA wrong expansion table, or a plugin pointed at its own package directory for writable data §9.1.

    Part A · A2 — the server actually runs

    This is the step that separates a demonstration from a self-check. The launch plan from A1 — command, arguments, environment, working directory — is executed verbatim as a subprocess, and the test speaks line-delimited JSON-RPC to it. Every request and response is printed.

    One deliberate deviation

    The plugin's env is layered over the process environment, not substituted for it. A subprocess started with only the plugin's four variables has no PATH and no SystemRoot, and on Windows would not start. A real client layers too; the code says so in a comment.

    #CheckWhat it would catch
    7initialize returns the protocol version and the server nameA plan that does not start, a wrong interpreter, a wrong working directory, or a handshake that does not answer.
    8tools/list returns add_note and list_notesA server that starts but exposes nothing usable.
    9list_notes reports an empty store before the first writeState leaking between runs. The test deletes notes.jsonl first, so this pins the starting point and makes checks 11 and 15 exact rather than approximate.
    10add_note confirms the writeA tool call that returns a result without doing the work.
    11list_notes returns both notes in orderA lost write, a wrong order, or a read path that disagrees with the write path.
    12an unknown tool returns a JSON-RPC error, and the server stays upA crash on bad input, or a silent success for a tool that does not exist. Error code -32602 is compared.
    13the server answers again after the errorA server that answers the error and then dies. This is the check that makes 12 mean something.

    Part A · A3 — the effect on disk

    Protocol replies are cheap to fake. These three look at the filesystem instead.

    #CheckWhat it would catch
    14notes.jsonl exists in PLUGIN_DATAA server that answered correctly but wrote nowhere, or wrote somewhere else.
    15it holds both records as line-delimited JSONCorrupt framing — the file must parse, one object per line, in order.
    16the server wrote nothing inside PLUGIN_ROOT §9.1Any write into the package. The test takes a full snapshot of every file's size and modification time before and after, so a new file and a modified file both fail. This is the check the mutation test trips.

    Part A · A4 — the data survives a restart

    #CheckWhat it would catch
    17the notes survive a restart of the serverState held only in memory. The whole reason ${PLUGIN_DATA} exists is that it outlives both the process and the next plugin update; a passing 14–16 with in-memory state would still fail here.

    Part A · A5 — the skill's script

    A skill may ship executable support. The tutorial's skill tells the agent to run scripts/check_entry.py, so the test runs it on a good file and a bad one.

    #CheckWhat it would catch
    18it accepts a valid entry (exit 0)A validator that rejects correct input — worse than no validator, because it trains the agent to ignore it.
    19it rejects sections in the wrong order (exit 1)A validator that passes everything. Exit code, not text, so a caller can branch on it.
    20the rejection names the reasonA failure the agent cannot act on. The string sections are out of order must appear.

    Part A · A6 — the two clients agree

    #CheckWhat it would catch
    21both reference clients produce the same launch planAny behavioral divergence. The entire result structure is compared after normalizing path spelling — not a summary, not the keys. A first-difference report names the exact JSON path when it fails, for example $.mcpServers.notes.env.NOTES_FILE.

    Part A · A7 — the smallest valid plugin

    The front page shows a four-file tree and a three-line manifest and calls it the smallest valid plugin. The test builds that plugin in a temporary directory from the page's own blocks and loads it. If the page ever describes something that is not loadable, these four fail.

    #CheckWhat it would catch
    22the smallest valid plugin loadsA claim on the front page that the client contradicts.
    23it needs no mcp.jsonA client that requires the optional file §6.2.
    24its one skill is discoveredDiscovery that depends on manifest declarations rather than on the directory.
    25it produces no warningA minimal, fully valid plugin that still emits noise. Silence is part of "valid".

    Part A · A8 — every documented command

    Four commands appear in the tutorial or the README. The test runs each and requires both exit 0 and the expected success line.

    #CommandWhat it covers
    26python loader.pyThe Python client's own self-check: manifest rejection cases, the non-fatal cases, skill discovery rules, MCP per-entry rules, and the single-pass expansion assertions.
    27npm testThe TypeScript compile under strict plus the same conformance cases. A type error fails here.
    28python bin/notes_server.py --self-checkThe server's handler logic without a subprocess: handshake, tool list, notification returns nothing, unknown method returns an error.
    29python scripts/check_entry.pyThe validator's own assertions.
    Read this before you trust the number 59

    Checks 26 and 27 are two results that stand for the whole of both self-check suites: 15 assertions and 8 manifest-rejection cases in loader.py, 17 assertions and a comparable rejection set in loader.ts. Every containment case and every expansion case hides behind those two lines. The number 59 counts reported results, not assertions. Do not read it as a measure of coverage depth.

    Part B · the pages describe what exists

    Documentation rots quietly: the code changes, the page does not, and the reader follows the page. These 30 checks turn that into a build failure. Every JSON block is comment-stripped with a string-aware scanner — a // inside "https://…" is not a comment — and then parsed and compared.

    #CheckWhat it would catch
    30plugin-authors.html shows exactly one annotated plugin.jsonA second, drifting copy of the manifest. Uniqueness first, so 31 compares the right block.
    31the annotated manifest equals the real plugin.jsonAny difference at all: a changed value, a key added on the page, a key removed from the file.
    32it uses all ten manifest keysThe tutorial's claim to be exhaustive quietly becoming false.
    33the page shows mcp.json in two partsA restructured page that leaves 34 comparing the wrong thing.
    34the two parts join into the real mcp.jsonAny drift between the annotated split view and the shipping file.
    35all three transports appearThe tutorial silently ceasing to cover a transport.
    36the name regex is printed onceTwo competing statements of the naming rule.
    37the printed regex is the one loader.py compilesA documented rule the implementation does not apply.
    38loader.py and loader.ts apply the same name regexTwo implementations disagreeing on which names are legal — a portability bug at the source level, caught even where check 21 could not see it.
    39the page shows the NOTES_FILE excerptThe excerpt disappearing while the prose still refers to it.
    40the excerpt appears verbatim in bin/notes_server.pyAn excerpt edited for the page and never applied to the code.
    41the page shows the SKILL.md frontmatterThe block being removed or restructured.

    53the sample output lists the servers the loader reportsSame, for names and transport types.

    Proof that the checks can fail

    A suite that has never been red is not evidence. One character in mcp.json was changed — ${PLUGIN_DATA} to ${PLUGIN_ROOT} — and four independent checks went red from that single edit:

    outputthe mutation run
    [FAIL] NOTES_FILE expands into PLUGIN_DATA, not into PLUGIN_ROOT
[FAIL] the server wrote nothing inside PLUGIN_ROOT (spec §9.1) — ['notes.jsonl']
[FAIL] the two parts join into example/changelog-tools/mcp.json
[FAIL] the tree names every file that exists — nothing is undocumented — ['notes.jsonl']
=== 55 passed, 4 failed ===
exit 1

    Note what the four failures are: one static check on the plan, one observation of the filesystem, one documentation-drift check, and one undocumented-file check. The same defect was caught from four independent directions, which is the property you want. The file was then restored and the suite returned to 59.

    What is not tested, and why

    The gaps below are known, not discovered later. Each has a reason.

    Not testedWhy
    The streamable-http server is never contacted. Only its launch plan is validated.https://releases.example.com/mcp does not exist, and neither reference client contains HTTP code. A test would need a real server and a network. Checks 3 and 21 cover the planning, which is the part the standard specifies.
    The sse transport is never implemented.Support is OPTIONAL §7.2.1 and both clients decline it. Check 4 tests the decision to decline, which is the conformant behavior.
    No agent ever performs the skill.Checks 18–20 run the script the skill names. Whether a model reading SKILL.md writes a good changelog is a model-quality question, not a specification question, and no deterministic test can settle it.
    references/format.md is never read or validated.Its existence is checked (49), and the skill points at it. Its contents are prose for a model; there is nothing to assert.
    com.example.client/hooks/hooks.json is never interpreted.Deliberate, and the point of the example. Agent Plugins gives that directory no meaning §8.1. A test that read it would be testing a client that does not exist.
    Malformed JSON-RPC input to the server.A real gap, not a justified one. main() calls json.loads(line) unguarded, so a malformed line kills the server. The 106-line example prefers legibility; production code uses an MCP SDK that owns framing and recovery. Named here rather than hidden.
    Concurrency, large payloads, timeouts, a hung or crashed server.Out of scope for a teaching example. A client that must survive a hostile plugin needs process supervision, and that is client policy, not specification behavior.
    POSIX. Everything here ran on Windows.The code uses os.path and path throughout and check 21 normalizes separators, but no run on Linux or macOS has been observed. Treat cross-platform behavior as untested.
    The ./bin/server command form and the ${PLUGIN_DATA} and ./sub cwd forms.Exercised only inside the loaders' self-checks (26, 27), not against the shipping example, which uses a bare python command and cwd: "${PLUGIN_ROOT}".
    Real JSON Schema validation.The standard library has no validator and the project takes no dependency. Checks 56–59 verify only that the printed schemas and the real files agree about which keys exist — not that the files satisfy the schemas.
    The tutorial's prose.Part B compares code blocks. A sentence that misstates §7.2.1 passes every check. Prose is reviewed by reading, and the tutorial cites a section for each rule so a reader can verify it against the specification.
    This page and the implementation page.Part B scans the four tutorial pages only. Adding these two would change the number of checks that this page exists to document. The one-line fix — extending the PAGES list in e2e.py — is left for whoever next edits the suite.
    Rendering: theme, layout, horizontal overflow, the table of contents.Verified once by hand in a real browser in both themes. Not automated; a browser engine is a dependency this project does not take.
    That the live site serves the current commit.Outside the suite. It is a deployment property, and a real one: three quick pushes once left the site serving an older commit while every URL still returned 200. Confirm with the deployment SHA, not with a status code.

    What 59 passes let you conclude

    Established

    • The tutorial is executable, not aspirational. The documented commands run, the documented plugin loads, the bundled server starts from the client's own plan, and the front page's minimal example is genuinely minimal and genuinely valid.
    • There is no hidden step between "plan" and "process". The client's output is directly executable: command, arguments, environment, working directory, spawn. A client author can copy that shape.
    • The data-durability rule holds in practice. Writes land in ${PLUGIN_DATA}, nothing enters ${PLUGIN_ROOT} — verified by full snapshot, not by inspection — and the data survives a restart.
    • Failure isolation holds for the case shown. One unsupported transport removes one server, reports one line, and leaves the other server and the skill loaded.
    • Two independent implementations agree completely. Same input, same output structure, character for character after path normalization.
    • Documentation drift is now a failure, not a discovery. Every block that claims to be a file is re-derived from the file on every run.

    Not established

    • Conformance to the specification. One example passing is one data point. There is no official conformance suite for Agent Plugins 1.0.0 — the tutorial says so in the reference — and a misreading of a rule that both clients share would pass every check here. The two implementations were written from the same reading, so their agreement reduces the chance of a coding mistake, not of a reading mistake.
    • Portability. Windows 11, Python 3.13.5, Node 22.22.0, one machine.
    • That any remote transport works. No HTTP request was ever made.
    • Robustness. The server was never given malformed input, concurrent input, or a large payload. It survives one bad tool name; that is all check 12 claims.
    • Security. Two escape cases are covered inside the loaders' self-checks — a ../ command and a nested SKILL.md. No symlink attack was constructed against the shipping example, and no adversarial plugin was written.
    • That the prose is correct. Only code is compared.
    The honest one-line summary

    59 passes mean the worked example does what the tutorial says it does, and the tutorial says what the files contain. They do not mean the specification is implemented correctly. Those are different claims, and only the first one has been measured.
