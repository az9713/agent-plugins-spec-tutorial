    Tutorial 2 — Implement an Agent Plugins Client

    A conformant client loads a plugin from a directory, validates the manifest, and supports at least one component type. This page walks the whole loading sequence, and pairs every rule with the reference code that implements it.

    Specification 1.0.0 Reference: example/client/loader.ts Also in Python: loader.py
    shell
    cd example/client
npm install
npm test                 # the self-check — every case in section 10
npm run load-example     # loads ../changelog-tools

    1 · What conformance means

    A conformant client satisfies every applicable requirement in sections 1 to 10 of the specification. At minimum it does eight things §11.1:

    1. It loads a plugin from a directory path.
    2. It selects locally supported rules from $schema, then validates the closed plugin.json schema, using the two non-fatal exceptions.
    3. It ignores an unimplemented extensions namespace, without validating its contents.
    4. It discovers each supported component type from its fixed location.
    5. If it supports MCP, it selects rules from the mcp.json $schema, and supports stdio or streamable-http.
    6. If it launches subprocesses, it provides PLUGIN_ROOT and PLUGIN_DATA, and expands both in args, env, and cwd.
    7. It resolves command as one executable token, and defaults the working directory to the plugin root.
    8. It supports at least one component type.
    Incremental adoption is legal

    A skills-only client conforms without any MCP support, provided it satisfies every rule that applies to it §11.2. You do not have to build everything at once.

    1.1 What the specification leaves to you

    None of these affects conformance. All of them are yours to design:

    • The install source, the registry, and the marketplace.
    • The enable, update, and cache user experience.
    • The permission prompt, the trust policy, and the sandbox.
    • How a skill reaches a user or a model.
    • The behavior inside your own extension namespace.

    2 · The six-step loading sequence

    1. Resolve the filesystem plugin root.
    2. Read and validate plugin.json, using the rules that $schema selects.
    3. Reject the plugin on a fatal violation. Report and ignore the two non-fatal cases.
    4. Discover each supported component type from its fixed location.
    5. Apply the failure boundary that belongs to that component type or entry.
    6. Apply your implemented extension namespaces. Ignore every other namespace.
    typescriptloader.ts — the whole sequence
    export function loadPlugin(
  rootIn: string,
  pluginDataIn?: string,
  transports: readonly string[] = ["stdio", "streamable-http"],
): LoadedPlugin {
  const root = fs.realpathSync(path.resolve(rootIn));                  // step 1

  // PLUGIN_DATA lives OUTSIDE the package. An update replaces the package
  // contents, and the data directory must survive that update (§9.1).
  const defaultData = path.join(path.dirname(root), ".plugin-data", path.basename(root));
  const wanted = path.resolve(pluginDataIn ?? defaultData);
  fs.mkdirSync(wanted, { recursive: true });
  const pluginData = fs.realpathSync(wanted);

  const reports: string[] = [];
  const report: Report = (msg) => reports.push(msg);
  const manifest = loadManifest(root, report);                          // steps 2 and 3

  return {
    name: manifest["name"] as string,
    manifest,
    skills: discoverSkills(root, report),                               // steps 4 and 5
    servers: loadMcp(root, manifest["$schema"] as string, pluginData, report, transports),
    extensions: (manifest["extensions"] ?? {}) as Record<string, unknown>,  // step 6
    reports,
  };
}
    Never fetch a schema

    The $schema value selects local rules. A client must not retrieve a schema while it loads a plugin §5.2, §7.2.1. A network fetch during load turns an offline user into a broken user, and it turns a URL owner into a supply-chain dependency.

    3 · Step 1 — the root and containment

    typescriptloader.ts
    /** Return true when p stays inside root after symlink resolution (§4.1). */
export function contained(p: string, root: string): boolean {
  const real = (x: string) => {
    try { return fs.realpathSync(x); } catch { return path.resolve(x); }
  };
  const rp = real(p);
  const rr = real(root);
  return rp === rr || rp.startsWith(rr + path.sep);
}
    Use realpath, not resolve

    path.resolve and os.path.abspath normalize a string. They do not follow a symlink. A package that ships skills/evil -> /etc passes a string check and fails a real check. The specification names symlinks, junctions, and reparse points explicitly §4.1.

    3.1 The failure-boundary ladder

    When a path fails containment, apply the narrowest boundary. Never widen it §4.1.

    #The path that failedThe required action
    1plugin.jsonReject the whole plugin.
    2A fixed component location, for example skills/Treat that component type as invalid. Keep the other types §6.2.
    3A discovered SKILL.mdSkip that skill. Keep the other skills §7.1.
    4An MCP command or cwdTreat that server entry as invalid. Keep the other servers §7.2.2.
    5Any other package pathDeny access to that path only.
    The most common conformance failure

    A client that rejects a whole plugin because one server has a bad cwd is not conformant. A plugin with a skill and a broken server must still deliver the skill §11.3.

    4 · Steps 2 and 3 — validate the manifest

    4.1 The closed field set

    typescriptloader.ts
    /** The ten permitted top-level manifest keys and their JSON types (§5.2). */
const MANIFEST_FIELDS: Record<string, "string" | "object" | "array"> = {
  $schema: "string", name: "string", version: "string", description: "string",
  author: "object", homepage: "string", repository: "string", license: "string",
  keywords: "array", extensions: "object",
};
const AUTHOR_FIELDS = new Set(["name", "email", "url"]);

/** All four name constraints of §5.5 in one pattern. */
const NAME_RE = /^(?!.*(?:--|\.\.))[a-z0-9](?:[a-z0-9.-]*[a-z0-9])?$/;

    4.2 The only two non-fatal cases

    typescriptloader.ts — loadManifest, abridged
    // Non-fatal case 1: an unknown top-level key (§5.2).
for (const key of Object.keys(m)) {
  if (!(key in MANIFEST_FIELDS)) {
    report(`unknown manifest field ignored: ${key}`);
    delete m[key];
  }
}

if (m["$schema"] !== PLUGIN_SCHEMA) {
  throw new Fatal(`unsupported $schema: ${JSON.stringify(m["$schema"])}`);
}
const name = m["name"];
if (typeof name !== "string" || name.length < 1 || name.length > 64 || !NAME_RE.test(name)) {
  throw new Fatal(`invalid name: ${JSON.stringify(name)}`);
}

for (const [key, kind] of Object.entries(MANIFEST_FIELDS)) {
  if (!(key in m)) continue;
  if (jsonKind(m[key]) === kind) continue;
  // Non-fatal case 2: extensions is not an object (§8.1).
  if (key === "extensions") {
    report("extensions is not an object; field ignored");
    m["extensions"] = {};
    continue;
  }
  throw new Fatal(`field ${key} has the wrong type`);
}
    CaseFatalAction
    An unknown top-level keyNoReport. Ignore. Continue.
    extensions is not an objectNoReport. Ignore. Continue.
    Missing file, invalid JSON, or a non-object rootYesReject the plugin.
    $schema missing or unrecognizedYesReject. Report the unsupported version.
    name missing, empty, or malformedYesReject. Report which field failed.
    A permitted key with a wrong JSON typeYesReject.
    A fourth author key, or a non-string valueYesReject.
    An extensions member value that is not an objectYesReject.

    4.3 Do not over-validate

    These rejections are forbidden

    A client must not reject a manifest solely because §5.4:

    • version is not valid Semantic Versioning;
    • homepage, repository, or author.url is not a recognized URL;
    • author.email is not a recognized email address;
    • license is not an SPDX identifier.

    Check the JSON type only, except where the specification states an explicit constraint. A client that adds a URL check breaks valid plugins, and is not conformant.

    5 · Step 4a — discover skills

    typescriptloader.ts
    export function discoverSkills(root: string, report: Report): Skill[] {
  const base = path.join(root, "skills");
  if (!fs.existsSync(base)) return [];                    // missing is not an error (§6.2)
  if (!fs.statSync(base).isDirectory()) {
    report("skills exists but is not a directory; skills disabled");
    return [];                                            // wrong kind: type invalid (§6.2)
  }
  const skills: Skill[] = [];
  for (const entry of fs.readdirSync(base).sort()) {      // immediate children ONLY (§7.1)
    const skillMd = path.join(base, entry, "SKILL.md");
    if (!fs.existsSync(skillMd) || !fs.statSync(skillMd).isFile()) continue;
    if (!contained(skillMd, root)) {
      report(`skill ${entry} escapes the plugin root; skipped`);
      continue;
    }
    skills.push({ name: entry, path: skillMd });
  }
  return skills;
}

    Four rules control this function:

    RuleBehaviorSection
    Missing locationNot an error. Return an empty list.§6.2
    Wrong filesystem kindThe component type is invalid. Other types still load.§6.2
    DepthImmediate children only. Never recurse.§7.1
    File kindSKILL.md must be a regular file with that exact name.§7.1

    Validate each discovered skill against the Agent Skills specification. When it fails, skip that skill, report it, and keep the others §7.1.

    6 · Step 4b — parse mcp.json

    6.1 The file level

    Four conditions disable MCP for the whole plugin, and the skills still load §7.2.2:

    1. The file is not valid JSON.
    2. The $schema value is unsupported.
    3. The $schema version differs from the plugin.json version §10.1.
    4. The top-level key set is not exactly {"$schema", "mcpServers"}, or mcpServers is not an object.
    typescriptloader.ts — loadMcp, abridged
    const keys = Object.keys(d).sort().join(",");
if (keys !== "$schema,mcpServers") {
  report("mcp.json has wrong top-level fields; MCP disabled");
  return {};
}
if (d["$schema"] !== MCP_SCHEMA) {
  report("mcp.json targets an unsupported version; MCP disabled");
  return {};
}
const versionOf = (id: string) => id.split("/").slice(-2)[0];
if (versionOf(d["$schema"] as string) !== versionOf(manifestSchema)) {
  report("mcp.json version differs from plugin.json; MCP disabled");      // §10.1
  return {};
}

    An empty mcpServers object is valid, and it is not an error §7.2.1.

    6.2 The entry level

    Each entry is a closed variant. An unknown key, an unknown type, or a key that belongs to another variant makes that entry invalid §7.2.1.

    VariantRequiredOptional
    stdiotype, commandargs, env, cwd
    streamable-httptype, urlheaders
    ssetype, urlheaders
    Why the schema exposes #/$defs/server

    The official MCP schema exposes the server definition so that you can validate one entry at a time. Validating the whole document as one unit destroys the per-entry failure boundary §7.2.1.

    6.3 Resolve command

    typescriptloader.ts — validateServer, stdio branch
    let command: string = rawCommand;
if (command.startsWith("./")) {
  const resolved = resolveRel(command, root);          // against the plugin root
  if (resolved === null) throw new Error("command escapes the plugin root");
  command = resolved;
} else if (command.includes("/") || command.includes("\\")) {
  throw new Error("command must be a bare name or a ./ path");
}
    RuleDetail
    One tokenNever parse the value as a shell string. Never escape it as one.
    A bare nameResolve through the platform executable search.
    A ./ pathResolve against the plugin root. It must stay inside.
    No expansionDo not expand a placeholder in this field §9.2.
    WindowsYou may use a command interpreter for a .bat or .cmd file. Keep command as one token, and pass args separately.
    PATHWhether your configured PATH affects a bare name is client-defined. A conformant plugin must not depend on it.

    6.4 Resolve cwd

    typescriptloader.ts
    const CWD_RE = /^(?:\.\/|\$\{PLUGIN_ROOT\}(?:\/|$)|\$\{PLUGIN_DATA\}(?:\/|$))/;

// ...
if (cwd === undefined) {
  cwdPath = root;                                                    // default (§7.2.1)
} else {
  if (typeof cwd !== "string" || !CWD_RE.test(cwd)) {
    throw new Error(`invalid cwd form: ${JSON.stringify(cwd)}`);
  }
  const source = cwd.startsWith("./") ? path.join(root, cwd.slice(2)) : cwd;
  cwdPath = path.normalize(expand(source, root, pluginData));         // expand FIRST
  const base = cwd.startsWith("${PLUGIN_DATA}") ? pluginData : root;  // correct base
  if (!contained(cwdPath, base)) throw new Error("cwd escapes its base directory");
}

    Five ordered rules §7.2.1:

    1. Absent cwd means the plugin root.
    2. The value must match one of the three legal forms. Any other form invalidates the entry.
    3. Expand the placeholders before you resolve the path.
    4. Check containment against the correct base: the plugin root for ./ and ${PLUGIN_ROOT}; the plugin data directory for ${PLUGIN_DATA}.
    5. Any escape after resolution invalidates the entry.

    6.5 Check a remote URL and its headers

    typescriptloader.ts — remote branch
    const LOOPBACK_RE = /^(?:localhost|127(?:\.\d+){3}|\[::1\])$/i;

const m = /^(https?):\/\/([^/?#]+)(?:[/?#]|$)/i.exec(url);
if (!m) throw new Error("url must be an absolute http or https URL");
const scheme = m[1]!.toLowerCase();
const host = m[2]!;
if (host.includes("@")) throw new Error("url must not contain user information");
if (url.includes("#")) throw new Error("url must not contain a fragment");
const hostname = host.startsWith("[") ? host.slice(0, host.indexOf("]") + 1)
                                      : host.split(":")[0]!;
if (scheme === "http" && !LOOPBACK_RE.test(hostname)) {
  throw new Error("http is allowed for a loopback host only");
}

const lowered = Object.keys(headers).map((k) => k.toLowerCase());
if (new Set(lowered).size !== lowered.length) {
  throw new Error("duplicate header name under different casing");
}
    Two security rules you must implement
    1. Your own header for HTTP, MCP, or authorization overrides a configured header with the same case-insensitive name §7.2.1.
    2. Never forward a configured header to a different origin after a redirect, or after a legacy SSE endpoint event, without explicit user authorization §7.2.1.

    Version 1 defines no OAuth field and no credential reference. Authorization discovery, the user interaction, and the credential storage are yours. An authorization failure is a connection failure, not invalid configuration §7.2.1.

    6.6 The five loading rules

    #ConditionRequired action
    1Any source other than root mcp.jsonNever load it.
    2The file level failsDisable MCP for the plugin. Keep the other component types. Report it.
    3One entry failsSkip that entry. Keep the others. Report it.
    4The declared transport is unsupportedSkip that entry. Report it.
    5The server fails to start, connect, authenticate, or handshakeContinue loading. Report it.

    7 · Step 6 — the subprocess environment

    7.1 The two variables

    VariableValueYour obligation
    PLUGIN_ROOTThe absolute resolved plugin root.Set it on every plugin subprocess.
    PLUGIN_DATAAn absolute path to a directory that you manage for this installed plugin instance.Create it before launch. Make it writable. Preserve it across an update. You may delete it on uninstall.
    Do not put the data directory inside the package

    An update replaces the package contents. A data directory inside PLUGIN_ROOT disappears with it, and the specification requires the opposite §9.1. The reference client defaults to a sibling directory:

    typescriptloader.ts
    const defaultData = path.join(path.dirname(root), ".plugin-data", path.basename(root));

    7.2 The order of assembly

    typescriptloader.ts
    // The client sets the reserved variables LAST (§9.1).
const finalEnv: Record<string, string> = {};
for (const [k, v] of Object.entries(envObj)) finalEnv[k] = expand(v, root, pluginData);
finalEnv["PLUGIN_ROOT"] = root;
finalEnv["PLUGIN_DATA"] = pluginData;
    1. Choose the base environment. You may inherit, omit, or clean the ambient variables.
    2. Expand the configured env values, and lay them over the base. A same-name entry replaces, under the platform name semantics — Windows names are case-insensitive.
    3. Set PLUGIN_ROOT and PLUGIN_DATA last. They replace any equivalent name.

    An env object that declares either reserved name makes that server entry invalid §9.2. Reject the entry. Do not silently drop the key.

    7.3 The expansion algorithm

    typescriptloader.ts
    const PLACEHOLDER_RE = /\$\{PLUGIN_ROOT\}|\$\{PLUGIN_DATA\}/g;

/**
 * Replace ${PLUGIN_ROOT} and ${PLUGIN_DATA} in ONE pass (§9.2).
 * String.replace with a function never rescans the inserted text. Two chained
 * replace calls would rescan, and a plugin could then inject a placeholder.
 */
export function expand(value: string, pluginRoot: string, pluginData: string): string {
  const table: Record<string, string> = {
    "${PLUGIN_ROOT}": pluginRoot,
    "${PLUGIN_DATA}": pluginData,
  };
  return value.replace(PLACEHOLDER_RE, (m) => table[m]!);
}
    The bug that a naive implementation ships

    Two chained replacements rescan the output of the first:

    typescriptwrong
    value.replace("${PLUGIN_ROOT}", root).replace("${PLUGIN_DATA}", data);

    If root itself contains the text ${PLUGIN_DATA}, the second call replaces text that the first call inserted. The specification forbids that: expansion is a single non-recursive replacement, and inserted text must not be scanned again §9.2.

    FieldExpands
    Each args elementYes
    Each env valueYes
    cwdYes
    An env keyNo
    commandNo
    url, a header name, a header valueNo
    A fixed component locationNo

    Unrecognized placeholder text stays literal. Perform no other expansion of any kind §9.2.

    8 · Step 6 — client extensions

    typescripta sketch, not part of the loader
    for (const [namespace, value] of Object.entries(plugin.extensions)) {
  const handler = this.handlers.get(namespace);
  if (!handler) continue;              // ignore, and do NOT validate the value (§8.1)
  handler.apply(value, path.join(root, namespace));   // the files live here (§8.2)
}
    1. Ignore a namespace that you do not implement. Do not validate its contents §8.1.
    2. When you implement file behavior for a namespace, read it from the top-level directory with exactly that name §8.2.
    3. Define your own validation and failure behavior inside your own namespace. The specification assigns none §8.

    Base your namespace on a domain that you control, and keep it stable §8.

    9 · Reporting

    The specification uses SHOULD for reporting. Silent failure still destroys a plugin author's ability to debug. Report these §11.3:

    • Each ignored unknown manifest field.
    • Each rejected plugin, with the reason.
    • Each skipped skill, with the reason.
    • Each invalid, unsupported, or mismatched MCP configuration.
    • Each skipped server entry, and each connection failure.

    Reporting an unsupported component type, an unsupported transport, or an unimplemented extension namespace is optional. None of those is an error §11.3.

    10.3 The expansion cases

    typescriptloader.ts — demo()
    assert(expand("${PLUGIN_ROOT}", "${PLUGIN_DATA}", "/d") === "${PLUGIN_DATA}", "no rescan");
assert(expand("a${PLUGIN_ROOT}b${PLUGIN_DATA}c", "/r", "/d") === "a/rb/dc", "both expand");
assert(expand("${OTHER}", "/r", "/d") === "${OTHER}", "unknown stays literal");

    The first case is the important one. A client that chains two replacements returns /d here, and that answer is wrong.

    11 · Conformance checklist

    From Appendix A of the specification. The specification text governs when the checklist disagrees with it.

    Plugin loader

    • Parse and validate plugin.json §5.1, §5.2.
    • Validate the required $schema and name fields §5.3.
    • Validate the name against the four constraints §5.5.
    • Report and ignore an unknown plugin.json field §5.2.
    • Ignore an unimplemented extensions namespace without validating its value §8.1.
    • Reject a package path that resolves outside the plugin root §4.1.
    • Discover an implemented file extension from its top-level namespace directory §8.2.

    Component discovery

    • Scan the fixed location for each supported component type §6.1.
    • Ignore a missing fixed location without an error §6.2.

    MCP configuration

    • Select a supported $schema, then validate the closed schema and each variant §7.2.1.
    • Implement stdio or Streamable HTTP §7.2.1.
    • Use the declared transport for the first connection attempt §7.2.1.
    • Enforce the remote URL rules and the literal-header rules §7.2.1.

    Environment and expansion

    • Provide PLUGIN_ROOT and a dedicated writable PLUGIN_DATA §9.1.
    • Resolve command as one bare or plugin-relative token §7.2.1.
    • Use the plugin root as the default working directory §7.2.1.
    • Validate the cwd form and the containment after resolution §7.2.1.
    • Lay the configured env over a base environment that you choose §9.1.
    • Set PLUGIN_ROOT and PLUGIN_DATA after the configured env §9.1.
    • Do not require a configured PATH to affect bare-command resolution §7.2.1.
    • Expand only the two placeholders, and only in args, env, and cwd §9.2.

    Resilience

    • Ignore an unsupported component type §11.3.
    • Skip a server with an unsupported transport, without affecting the others §7.2.2.
    • Continue loading when an independent component fails §11.3.
    • Support at least one component type §11.1.

    What the loader does not do

    It returns a launch plan. It does not spawn the process, open the connection, prompt for trust, or draw a user interface. Those parts are yours, and the specification does not constrain them.

    13 · Design for what comes next

    Version 1 leaves these to you. A future version may standardize them, so keep each one behind an interface:

    1. A permission model, a capability declaration, and a sandbox.
    2. Signature verification and a provenance attestation chain.
    3. A portable secret mechanism, instead of plaintext in a config file.
    4. An enterprise allowlist, a blocklist, and a central override.
    5. A standard audit event schema for install, enable, disable, update, and uninstall.
    6. Dependencies between plugins, with version constraints.
    7. A conformance test suite.
